> 개요: 이 챕터에서는 알고리즘을 말로 설계하는 수도코드부터 시작해, 입력이 커질 때 코드가 얼마나 느려지고 메모리를 얼마나 쓰는지를 수학적으로 예측하는 시간·공간복잡도 분석(Big-O)을 배운다.

## L1. 수도코드

**개념**

- 수도코드(pseudocode)는 특정 언어 문법에 얽매이지 않고 알고리즘의 논리 흐름만 사람이 읽기 쉽게 적은 "설계도"다. 코드를 바로 짜기 전에 아이디어를 검증하고, 남에게 로직을 설명하고, 복잡도를 따지기 위한 뼈대를 잡는 데 쓴다.
- 왜 필요한가: 문제를 보자마자 파이썬을 치기 시작하면 인덱스 실수·조건 누락에 파묻혀 큰 그림을 놓친다. 수도코드는 "무엇을 어떤 순서로 하는가"만 남기고 세부 문법(세미콜론, `range` 경계 등)을 지워, 논리 오류를 코딩 전에 잡게 해준다.
- 동작 원리(작성 절차):

  - 1단계: 입력과 출력을 한 문장으로 못 박는다("정수 배열 A가 주어지면 최댓값을 반환").
  - 2단계: 큰 단계를 순서대로 나열한다(초기화 → 반복 → 갱신 → 반환).
  - 3단계: 각 단계를 분기(IF)·반복(FOR/WHILE)·대입(←)으로 구체화한다.
  - 4단계: 손으로 작은 예제를 한 번 굴려 논리를 검산한다.

- 표기 관례: 대입은 `←`, 비교는 `=`, 반복은 `for each`/`while`, 들여쓰기로 블록을 표현한다. 정답은 없고, 팀이 읽을 수 있으면 된다.

```text
FUNCTION find_max(A):
    IF A is empty:
        RETURN None
    best < A[0]
    FOR each x in A[1..end]:
        IF x > best:
            best < x
    RETURN best
```

**그림으로 보기**

- 수도코드는 "덜 쓴 코드"가 아니라 **추상 수준의 사다리에서 한 칸 위**다. 위 칸에서 잡은 버그는 한 줄 고치면 되지만, 아래 칸에서 잡으면 다시 쓰게 된다.

```text
 lv3  intent      "find the largest score"
 lv2  step list   init -> scan -> compare -> return
 lv1  pseudocode  best <- A[0] ; FOR x IN A : IF x > best : best <- x
 lv0  python      best = a[0] ; for x in a: if x > best: best = x
 -------------------------------------------------------------------
 a logic bug at lv1 costs one line ; at lv0 it costs a rewrite
```

- 수도코드가 복잡도 수업의 **첫 레슨인 이유**는 따로 있다. 각 줄 옆에 "이 줄이 몇 번 도는가"를 적어두면, 그 숫자를 더한 것이 그대로 `T(n)`이 된다. 다음 레슨의 Big-O는 이 표에서 지배항만 남기는 작업이다.

```text
 FUNCTION find_max(A):              # times   (n = len(A))
     IF A is empty:                 1
         RETURN None                0 or 1
     best <- A[0]                   1
     FOR each x in A[1..end]:       n-1
         IF x > best:               n-1
             best <- x              0 .. n-1
     RETURN best                    1
 -------------------------------------------------------------
 T(n) = 1 + 1 + (n-1) + (n-1) + (n-1) + 1  <=  3n + 1   ->  O(n)
```

**손으로 따라가기**

`A = [3, 9, 2, 9]`로 위 수도코드를 굴린다. 상태는 `best` 하나뿐이다.

| 단계 | 보는 값 `x` | 비교 `x > best` | 실행되는 줄 | `best` |
|---|---|---|---|---|
| 초기화 | – | – | `best ← A[0]` | 3 |
| 1 | 9 | 9 > 3 참 | `best ← x` | 9 |
| 2 | 2 | 2 > 9 거짓 | (갱신 없음) | 9 |
| 3 | 9 | 9 > 9 **거짓** | (갱신 없음) | 9 |
| 반환 | – | – | `RETURN best` | 9 |

- 답 `9`. 3단계가 설계의 갈림길이다. 비교를 `>=`로 바꾸면 답은 같지만 "**마지막** 최댓값의 위치"를 원할 때 결과가 달라진다. 수도코드 단계에서 이 결정을 못 박아 두는 것이 목적이다.

- 빈 리스트를 넣으면 `IF A is empty` 한 줄만 실행되고 끝난다. 손으로 굴려 볼 입력에 **경계 입력(빈 것·원소 1개·전부 동일)**을 꼭 하나 섞는다.

**왜 이렇게 되는가**

- **왜 문법을 지우는가**: 알고리즘의 정확성은 "무엇을 어떤 순서로 하는가"에서 나오고, 언어 문법은 그것을 옮겨 적는 수단일 뿐이다. `range` 경계나 들여쓰기 같은 표기 문제와 논리 문제를 **동시에** 다루면 사람은 대개 표기 쪽에 붙잡혀 논리 오류를 놓친다. 수도코드는 둘을 분리하는 장치다.

- **반복문이 옳다는 것을 어떻게 아는가 — 불변식(loop invariant)**: 수도코드에서 반복을 검증하는 표준 도구는 "반복이 한 바퀴 돌 때마다 항상 참인 명제"를 하나 정하는 것이다. `find_max`의 불변식은 다음과 같다.

  - **불변식**: 반복이 `A[k]`까지 처리한 시점에서 `best`는 `A[0..k]`의 최댓값이다.
  - 초기(initialization): `k = 0`일 때 `best = A[0]`이므로 참.
  - 유지(maintenance): `A[k+1]`을 볼 때 `A[k+1] > best`면 `best`를 그것으로 갱신하고, 아니면 그대로 둔다. 어느 쪽이든 `best`는 `A[0..k+1]`의 최댓값이 된다.
  - 종료(termination): 반복이 끝나면 `k = n-1`이므로 `best`는 `A[0..n-1]` 전체의 최댓값 — 곧 원하는 답이다.

  이 세 줄만 확인하면 원소 개수와 무관하게 알고리즘이 옳다. 예제 몇 개를 돌려 보는 것과 달리 **모든 입력에 대한 보증**이라는 점이 다르다.

- **종료 조건이 왜 별도 항목인가**: 반복은 "무엇을 하는가"와 "언제 멈추는가" 두 가지로 이루어지는데, 후자를 빼먹어도 수도코드는 문법 오류를 내지 않는다(사람이 읽고 넘어간다). 그래서 종료 조건은 항상 **명시적으로 한 줄** 적는다 — `while i < len(A) AND j < len(B)`처럼 어떤 변수가 어디까지 가면 끝인지가 보여야 한다.

- **왜 `←`와 `=`를 구분하는가**: 대입과 비교를 같은 기호로 쓰면 "값을 바꾸는 줄"과 "값을 묻는 줄"이 섞여 실행 횟수를 셀 수 없게 된다. 위 실행 횟수 표에서 `best ← x`(조건부, 0~n-1번)와 `IF x > best`(무조건, n-1번)의 횟수가 다른 것을 보라. 이 구분이 곧 최선·최악의 차이를 만든다.

- **수도코드는 복잡도를 갖지 않는다**: 실행물이 아니기 때문이다. 대신 각 줄의 실행 횟수를 세면 그 알고리즘의 `T(n)`이 나오고, 그 `T(n)`을 Big-O로 줄이는 것이 이 챕터의 나머지 전부다. 그래서 수도코드를 쓸 때부터 **반복문 옆에 횟수를 적는 습관**을 들이면 분석이 공짜로 따라온다.

**접근 전략**

- 핵심 아이디어: "코드를 짜기 전에 말로 먼저 푼다." 자연어 → 단계 목록 → 제어구조 순으로 추상 수준을 낮춰간다. 문제 지문을 그대로 옮기지 말고, "반복되는 작업"과 "언제 멈추는가(종료 조건)"를 반드시 명시한다.
- 언제 쓰나: 로직이 조금이라도 복잡하거나(중첩 반복, 여러 분기), 남에게 설명·리뷰가 필요할 때. 반대로 한 줄짜리 변환은 수도코드가 오히려 낭비다.
- 복잡도: 수도코드 자체는 실행물이 아니라 복잡도가 없다. 대신 각 반복/재귀 줄 옆에 "이 줄이 몇 번 도는가"를 주석으로 달아두면 다음 레슨의 시간복잡도 분석이 그대로 이어진다. 흔한 실수: 종료 조건을 빼먹어 무한 루프 논리를 그리는 것, 그리고 수도코드에 파이썬 문법을 섞어 "반쯤 코드"로 만드는 것(추상화 이점이 사라진다).

**문제**

**1) 성적 통과자 세기 설계** · Easy

- **요구사항**: 정수 점수 리스트와 기준 점수 `k`가 주어질 때 `k` 이상인 점수의 개수를 세는 알고리즘을 수도코드로만 설계하라(파이썬 코드 금지). 초기화·반복·조건·반환 네 단계가 드러나야 한다.
- **입력**: 점수 리스트 `scores`, 정수 `k`
- **출력**: `k` 이상인 원소의 개수(수도코드 텍스트)
- **예제**: `scores=[70, 55, 90, 60], k=60` → `3` / `scores=[10, 20], k=100` → `0`
- **셀프체크**: 종료 조건(리스트 끝)을 명시했는가? 카운터 초기값 0을 빠뜨리지 않았는가? 빈 리스트일 때도 0을 반환하는가?

```runner
@@SOLUTION
import sys
data = sys.stdin.read().split('\n')
scores = list(map(int, data[0].split())) if data[0].strip() else []
k = int(data[1])
print(sum(1 for x in scores if x >= k))
@@TESTS
--IN
70 55 90 60
60
--OUT
3
--IN
10 20
100
--OUT
0
@@EXPL
**이 풀이의 새 문법**

- `sum(1 for x in scores if x >= k)`: 제너레이터 표현식. `[1 for x in ... if ...]`(리스트 컴프리헨션)과 비슷하지만 대괄호 없이 값을 하나씩 흘려보내며, `sum()`처럼 함수 인자가 하나뿐이면 괄호도 생략할 수 있다. 조건을 만족할 때마다 1이 하나씩 나와 그 합이 곧 개수가 된다.

(1) 접근·핵심 아이디어

- 수도코드가 요구하는 "초기화 → 반복 → 조건 → 반환" 네 단계를 그대로 실행 코드로 옮긴 것이다. 카운터를 0으로 두고, 리스트를 한 번 훑으며 `k` 이상이면 세고, 끝나면 합계를 반환한다. 전체 `O(n)`.

(2) 코드 단계별

- 첫 줄에 점수들, 둘째 줄에 기준 `k`를 받는다. 첫 줄이 비어 있으면 빈 리스트로 처리해 "빈 입력도 0" 조건을 만족한다.
- `sum(1 for x in scores if x >= k)`가 곧 "카운터 초기화 0 + 조건 만족마다 +1"을 한 줄로 압축한 형태다.

(3) 스스로 다시 짤 때 생각 순서

- 먼저 세는 값(카운터)을 0으로 초기화한다고 못 박는다.
- 리스트를 처음부터 끝까지 도는 반복을 잡고, 종료 조건이 "리스트 끝"임을 명시한다.
- 반복 몸통은 `x >= k`일 때만 카운터를 늘리는 단일 조건.
- 반복이 끝나면 카운터를 반환. 빈 리스트면 반복이 0번 돌아 자연히 0이 나온다.
```

**2) 두 정렬 배열 병합 설계** · Medium

- **요구사항**: 각각 오름차순 정렬된 두 배열 A, B를 하나의 오름차순 배열로 합치는 과정을 수도코드로 설계하라. 두 포인터가 어떻게 움직이고 어느 쪽을 언제 고르는지, 한쪽이 먼저 소진되면 어떻게 되는지를 분명히 하라.
- **입력**: 정렬된 배열 A, B
- **출력**: 병합된 정렬 배열의 수도코드
- **예제**: `A=[1,3,5], B=[2,4]` → `[1,2,3,4,5]` / `A=[], B=[7]` → `[7]`
- **셀프체크**: 두 값이 같을 때의 처리가 정의되어 있는가? 한쪽 소진 후 남은 원소를 "꼬리 이어붙이기"로 처리했는가? 포인터 종료 조건이 `while i<len(A) AND j<len(B)`인가?

```runner
@@SOLUTION
import sys
data = sys.stdin.read().split('\n')
A = list(map(int, data[0].split())) if len(data) > 0 and data[0].strip() else []
B = list(map(int, data[1].split())) if len(data) > 1 and data[1].strip() else []
i = j = 0
out = []
while i < len(A) and j < len(B):
    if A[i] <= B[j]:
        out.append(A[i]); i += 1
    else:
        out.append(B[j]); j += 1
out.extend(A[i:])
out.extend(B[j:])
print(' '.join(map(str, out)))
@@TESTS
--IN
1 3 5
2 4
--OUT
1 2 3 4 5
--IN

7
--OUT
7
@@EXPL
(1) 접근·핵심 아이디어

- 두 포인터 `i`, `j`로 A와 B의 현재 후보를 가리키고, 둘 중 더 작은(같으면 A쪽) 값을 결과에 붙이며 그쪽 포인터만 전진시킨다. 한쪽이 소진되면 남은 쪽을 통째로 꼬리에 이어붙인다. 전체 `O(len(A)+len(B))`.

(2) 코드 단계별

- 첫 줄 = A, 둘째 줄 = B. 빈 줄이면 빈 리스트로 처리(예: A가 비고 B=[7]).
- `while i<len(A) and j<len(B)`가 정확히 셀프체크의 종료 조건. 몸통에서 `A[i] <= B[j]`로 같을 때는 A를 먼저 골라 안정적(stable) 병합을 보장한다.
- 루프 종료 후 `A[i:]`, `B[j:]` 중 남은 잔여를 그대로 확장 — 이것이 "꼬리 이어붙이기".

(3) 스스로 다시 짤 때 생각 순서

- 두 정렬 배열의 맨 앞을 비교하는 그림을 먼저 떠올린다.
- 작은 쪽을 뽑고 그 포인터만 +1 하는 규칙을 세운다(같을 때 어느 쪽을 먼저 뽑을지 결정).
- 한쪽 포인터가 끝에 닿으면 루프 종료 조건에 걸린다는 것을 확인.
- 루프 밖에서 아직 안 뽑힌 나머지를 이어붙이면 완성.
```

**3) 최소 거스름돈 동전 개수 설계** · Medium

- **요구사항**: 동전 단위 `[500,100,50,10]`과 금액 `n`이 주어질 때, 큰 단위부터 최대한 사용해 필요한 동전 개수를 구하는 과정을 수도코드로 설계하라(그리디 아이디어). 나눗셈 몫과 나머지가 어떻게 쓰이는지 드러나야 한다.
- **입력**: 정수 금액 `n`(단위는 위 4종으로 고정)
- **출력**: 최소 동전 개수의 수도코드
- **예제**: `n=1260` → `2+2+1+1 = ... ` 즉 `500×2, 100×2, 50×1, 10×1` → 총 `6` / `n=40` → `4`
- **셀프체크**: `n=1260`을 손으로 굴리면 500×2(잔액260)→100×2(잔액60)→50×1(잔액10)→10×1(잔액0)=6개가 맞는가? 남은 금액 갱신 단계를 매 단위마다 넣었는가?

```runner
@@SOLUTION
import sys
n = int(sys.stdin.readline())
coins = [500, 100, 50, 10]
cnt = 0
for c in coins:
    cnt += n // c
    n %= c
print(cnt)
@@TESTS
--IN
1260
--OUT
6
--IN
40
--OUT
4
@@EXPL
(1) 접근·핵심 아이디어

- 그리디: 가장 큰 단위부터 최대한 많이 쓴다. 각 단위 `c`에 대해 `n // c`가 그 단위를 쓰는 개수, `n % c`가 다음 단위로 넘길 잔액이다. 이 동전 집합은 배수 관계라 그리디가 최적을 보장한다. 반복 4번이라 `O(1)`.

(2) 코드 단계별

- 금액 `n`을 읽고 큰 단위 순 리스트 `[500,100,50,10]`을 준비.
```

## L2. 점근 표기법

**개념**

- 점근 표기법(asymptotic notation)은 입력 크기 `n`이 무한히 커질 때 알고리즘 비용(연산 횟수·메모리)이 "어떤 함수처럼 자라는가"를 나타내는 언어다. 실제 실행 시간(초)은 컴퓨터·언어마다 다르므로, 대신 성장 속도(growth rate)만 뽑아 비교한다.
- 왜 필요한가: `3n+7`이든 `100n`이든 `n`이 커지면 둘 다 "직선으로 자라는" 같은 급이다. 상수 계수와 낮은 차수 항은 큰 `n`에서 무의미해지므로 지워버리고 지배항(dominant term)만 남긴다. 이렇게 하면 알고리즘끼리 기계 독립적으로 비교할 수 있다.
- 세 가지 표기:

  - Big-O(O): 상한. "아무리 나빠도 이보다 빠르게는 안 자란다"(상계). 우리가 제일 자주 쓰는 최악의 경우 보증.
  - Big-Omega(Ω): 하한. "적어도 이만큼은 자란다."
  - Big-Theta(Θ): 상·하한이 같을 때. "정확히 이 급으로 자란다."

- 단순화 규칙: (1) 상수 계수 제거 `O(3n)=O(n)`, (2) 낮은 차수 항 제거 `O(n²+n)=O(n²)`, (3) 곱은 유지 `O(n·log n)`. 흔한 등급 순서(느린 성장 → 빠른 성장): `O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(2ⁿ) < O(n!)`.
- `log n` 직관: `n`을 절반씩 몇 번 나누면 1이 되는가(= 2를 몇 번 곱해야 `n`이 되는가). 예) `n=8` → 8→4→2→1로 3번이라 `log₂8=3`. 그래서 매번 절반으로 줄이는 이진탐색이 `O(log n)`이다.

```python
# 각 표현이 속하는 Big-O 등급 (n이 커질 때의 지배항만 남긴다)
# 5           -> O(1)      상수
# 3*n + 100   -> O(n)      선형
# n**2 + 500*n-> O(n**2)   낮은 차수(500n) 제거
# n * (n-1)/2 -> O(n**2)   전개하면 n²/2 지배
# import math; math.log2(n) -> O(log n)
```

**그림으로 보기**

- 등급의 순서를 외우는 것보다 **얼마나 벌어지는지**를 한 번 보는 게 훨씬 오래 간다. 아래는 `n = 1000`일 때 각 등급의 연산 횟수를 **자릿수 막대**로 그린 것이다(막대 한 칸 = 자릿수 1개 = 10배).

```text
 cost at n = 1000 ,  one '#' = one decimal digit  ( x10 )
 -------------------------------------------------------------
 O(1)             1        #
 O(log n)        10        ##
 O(n)          1 000       ####
 O(n log n)   10 000       #####
 O(n^2)     1 000 000      #######
 O(n^3)        10^9        ##########
 O(2^n)       10^301       ############### ... 302 marks
 -------------------------------------------------------------
 this bar is a log scale : one more '#' means "ten times slower"
```

- `O(n)`과 `O(n log n)` 사이는 막대 한 칸 차이지만, `O(n)`과 `O(n²)`는 세 칸(1000배)이고 `O(2ⁿ)`는 아예 종이 밖으로 나간다. **코테에서 등급 하나를 낮추는 일이 상수 최적화보다 압도적으로 중요한 이유**가 이 그림에 다 들어 있다.

- 등급을 판정하는 가장 실용적인 도구는 **"`n`을 2배로 하면 비용이 몇 배가 되는가"**다. 등급마다 배율이 다르므로 지문이나 실측만으로 등급을 역산할 수 있다.

```text
 doubling test :  n  ->  2n
 -------------------------------------------------------------
 O(1)        1     ->  1            x 1      flat
 O(log n)    k     ->  k + 1        + 1      one more step
 O(n)        n     ->  2n           x 2
 O(n log n)  n*k   ->  2n*(k+1)     x 2.2    ( k = 10 )
 O(n^2)      n^2   ->  4 n^2        x 4
 O(n^3)      n^3   ->  8 n^3        x 8
 O(2^n)      2^n   ->  (2^n)^2      squared  ! ! !
 -------------------------------------------------------------
 the doubling factor is the fingerprint of a complexity class
```

- `O(n)`의 `x2`와 `O(n log n)`의 `x2.2`는 실측에서 구분하기 어렵다. 그럴 땐 **`n`을 네 배·여덟 배로 늘려** 배율이 `4 / 8`에 붙는지(선형) `4.4 / 9`쪽으로 벌어지는지(선형로그) 본다.

**손으로 따라가기**

Big-O 정의를 실제 숫자로 확인해 보자. `f(n) = 3n + 7`이 `O(n)`이라는 주장은 "**어떤 상수 `c`와 `n₀`가 존재해서, `n ≥ n₀`인 모든 `n`에 대해 `3n + 7 ≤ c·n`**"이라는 뜻이다. `c = 4`로 잡아 보자.

| `n` | `f(n) = 3n+7` | `c·n = 4n` | `f(n) ≤ 4n` ? |
|---|---|---|---|
| 1 | 10 | 4 | 거짓 |
| 3 | 16 | 12 | 거짓 |
| 7 | 28 | 28 | **참**(등호) |
| 8 | 31 | 32 | 참 |
| 100 | 307 | 400 | 참 |
| 10⁶ | 3 000 007 | 4 000 000 | 참 |

- `c = 4`, `n₀ = 7`을 제시하면 증명 끝. **작은 `n`에서 몇 번 어긋나는 것은 전혀 문제가 되지 않는다** — 정의가 `n ≥ n₀`만 요구하기 때문이다. 이것이 "상수·저차항을 버려도 되는" 형식적 근거다.

이번엔 상수가 큰 선형과 계수가 작은 이차를 비교한다. `A(n) = 100n + 5000`, `B(n) = 2n²`.

| `n` | `A(n)` | `B(n)` | 더 빠른 쪽 |
|---|---|---|---|
| 10 | 6 000 | 200 | B |
| 40 | 9 000 | 3 200 | B |
| 80 | 13 000 | 12 800 | B (아슬아슬) |
| 81 | 13 100 | 13 122 | **A**(역전) |
| 200 | 25 000 | 80 000 | A |
| 1 000 | 105 000 | 2 000 000 | A |

- 교차점 `n₀ = 81` 이후로는 **다시는 뒤집히지 않는다.** 점근 표기가 "작은 입력에서 누가 빠른가"를 버리고 "충분히 큰 `n`에서 누가 이기는가"만 말하는 이유가 이 표다. 반대로 `n`이 항상 50 이하로 작다면 Big-O만 보고 A를 고르는 것은 실수다.

**왜 이렇게 되는가**

- **Big-O의 정의를 말로 풀면**: `f(n) = O(g(n))`은 "**어떤 양의 상수 `c`와 어떤 시작점 `n₀`를 잘 고르면, `n₀`보다 큰 모든 `n`에서 `f(n)`이 `c·g(n)`을 넘지 않는다**"는 뜻이다. 핵심 단어는 두 개다.

  - `c`가 **존재하기만** 하면 된다 → 상수 배는 등급을 바꾸지 못한다.
  - `n₀`부터만 보면 된다 → 작은 `n`에서의 역전은 무시된다.

- **왜 상수 계수를 버리는가**: `f(n) = 5n`이라면 `c = 5`, `n₀ = 1`로 두면 `5n ≤ 5·n`이 항상 참이다. 즉 `O(n)`. `c`를 우리가 고를 수 있으므로 **계수는 언제나 `c` 안으로 흡수된다.** 이것이 `O(3n) = O(n)`, `O(n/2) = O(n)`인 이유다.

- **왜 낮은 차수 항을 버리는가**: `f(n) = n² + 100n`을 보자. `n ≥ 100`이면 `100n ≤ n²`이므로 `f(n) ≤ 2n²`이다. `c = 2`, `n₀ = 100`으로 정의를 만족하니 `O(n²)`. 일반적으로 차수가 낮은 항은 `n`이 커지면 최고차항 하나에 **통째로 삼켜진다** — 그래서 "지배항만 남긴다"는 규칙이 나온다.

- **왜 로그의 밑을 안 쓰는가**: 밑 변환 공식에 따라 `log₂n = log₁₀n / log₁₀2`이고 `1 / log₁₀2 ≈ 3.32`는 상수다. 밑이 무엇이든 서로 **상수 배**일 뿐이므로 위의 `c` 안으로 흡수된다. 그래서 `O(log₂n)`, `O(log₁₀n)`을 구분하지 않고 전부 `O(log n)`이라 쓴다. (반대로 `O(2ⁿ)`과 `O(3ⁿ)`은 상수 배가 아니라 **`(3/2)ⁿ`배** 차이라 절대 같은 등급이 아니다.)

- **`O` · `Ω` · `Θ`의 관계**: `O`는 위에서 누르는 뚜껑(상한), `Ω`는 밑에서 받치는 바닥(하한), `Θ`는 둘이 같은 등급일 때다. 정렬을 비교 기반으로 하면 `Ω(n log n)`이라는 하한이 알려져 있고, 병합 정렬은 `O(n log n)`이므로 둘을 합쳐 `Θ(n log n)`이라 말할 수 있다.

- **왜 "타이트한" 상한을 말해야 하는가**: `O`는 상한일 뿐이라 `O(n)`인 알고리즘을 `O(n²)`이라 말해도 **정의상 거짓은 아니다**(더 헐거운 뚜껑도 뚜껑이다). 하지만 그런 답은 아무 정보도 주지 못한다. 분석의 목표는 항상 **`Θ`에 가장 가까운 `O`**를 찾는 것이다.

- **덧셈과 곱셈 규칙의 근거**: 두 블록이 나란히 실행되면 `f(n) + g(n) ≤ 2·max(f, g)`이므로 **합은 큰 쪽으로 흡수된다**(`O(n) + O(n) = O(n)`, `O(n) + O(n²) = O(n²)`). 반면 중첩되면 바깥 횟수마다 안쪽이 통째로 돌므로 **곱**이 된다(`O(n) × O(log n) = O(n log n)`). 이 두 규칙이 다음 두 레슨(반복문·재귀)의 계산 전부를 떠받친다.

**접근 전략**

- 핵심 아이디어: 비용 함수를 구한 뒤 "가장 빨리 자라는 항 하나"만 남기고 계수를 떼면 그게 Big-O다. 어떤 항이 지배하는지는 `n`을 아주 크게(예: 10⁶) 대입해 상상하면 직관이 온다. `n²`은 `n`보다 압도적으로 커지므로 `n²+n → O(n²)`.
- 언제 쓰나: 알고리즘을 고르거나(정렬을 `O(n²)`로 짤지 `O(n log n)`으로 짤지), 제한 시간 안에 들어오는지 가늠할 때. 코테에서 `n ≤ 10⁶`면 대략 `O(n)`·`O(n log n)`까지 안전, `n ≤ 2000`이면 `O(n²)`도 통과가 기준선이다.
- 복잡도(주의점): Big-O는 상한일 뿐이라 `O(n)`인 코드를 `O(n²)`이라 말해도 "틀린 상한"은 아니지만 무의미하다. 가능한 한 타이트한(Θ에 가까운) 상한을 말하라. 흔한 실수: 상수를 남기거나(`O(2n)`이라 쓰기), 로그의 밑을 표기하는 것(밑은 상수라 `O(log n)`으로 통일), `O(n)+O(n)=O(n)`인데 `O(2n)`이라 착각하는 것.

**문제**

**1) Big-O 등급 매기기** · Easy

```runner
- 각 항의 성장 등급을 매긴다: 상수 < log n < n < n log n < n^2 < 2^n.
- 그중 최상위 등급만 남기고 계수(1/2, 4, 2 등)를 버린다.
- 그 최상위 등급이 곧 답. 등급 비교가 애매하면 큰 n(예: 10^6)을 상상해 대소를 확인.
```

**2) 두 알고리즘 중 빠른 것 고르기** · Medium

- **요구사항**: 같은 문제를 푸는 알고리즘 A는 연산 `100n + 5000`번, 알고리즘 B는 `2n²`번 한다. (a) 각각의 Big-O, (b) 어떤 `n`부터 A가 B보다 실제로 빨라지는지 경계값을 구하라.
- **입력**: 두 비용 함수(위)
- **출력**: `(a)` A·B의 Big-O, `(b)` A가 유리해지는 최소 정수 `n`
- **예제**: `n=10` → A=6000, B=200이라 B가 빠름 / `n=100` → A=15000, B=20000이라 A가 빠름
- **셀프체크**: `2n² > 100n+5000`을 풀면 `n²-50n-2500>0`, 근은 `n≈(50+√(2500+10000))/2 ≈ 80.9` → `n=81`부터 A가 빠른가? `n=81`에서 A=13100, B=13122로 A가 빠른지 검산했는가?

```runner

def B(n): return 2 * n * n
data = sys.stdin.read().split()

for m in range(1, 1000000):
    if A(m) < B(m):
        thr = m
        break
faster = 'A' if A(n) < B(n) else 'B'
print(faster, thr)
@@TESTS

--IN

(1) 접근·핵심 아이디어

- (a) A=100n+5000은 선형 `O(n)`, B=2n^2은 이차 `O(n^2)`. (b) 작은 n에서는 B가 빠르지만 n이 커지면 이차인 B가 결국 더 느려진다. 교차점은 `2n^2 > 100n+5000` 즉 `n^2-50n-2500>0`의 정수 해 시작점 n=81.

(2) 코드 단계별

- 비용 함수 A, B를 그대로 함수로 정의.
- `m=1`부터 올려가며 처음으로 `A(m) < B(m)`이 되는 m을 찾아 교차 임계값 `thr`로 저장 → 81이 나온다.
- 주어진 n에서 어느 쪽이 더 적은 연산인지(`faster`) 판정해 함께 출력. n=10이면 B(200)<A(6000)이라 B, n=100이면 A(15000)<B(20000)이라 A.

(3) 스스로 다시 짤 때 생각 순서

- 두 비용 함수를 코드로 그대로 옮긴다.
- 각 함수의 지배항으로 Big-O를 읽는다(A→n, B→n^2).
- 교차점은 부등식을 풀거나, 여기처럼 m을 1씩 올리며 처음 뒤집히는 지점을 스캔해 찾는다.
- 특정 n에서의 승자는 두 값을 직접 비교. n=81에서 A=13100<B=13122로 A가 앞서는지 검산.
```

**3) 등급 정렬** · Easy

- **요구사항**: 아래 Big-O 표현들을 `n`이 클 때 느리게 자라는 것부터 빠르게 자라는 순으로 나열하라.

## L3. 시간복잡도의 정의

**개념**

- 시간복잡도(time complexity)는 입력 크기 `n`에 대해 알고리즘이 수행하는 기본 연산 횟수를 함수 `T(n)`으로 나타낸 것이다. 실제 시간(초)이 아니라 "연산 횟수의 증가 추세"를 재며, 보통 Big-O로 표현한다.
- 왜 연산 횟수인가: 초 단위 측정은 CPU·언어·입력값에 따라 흔들린다. 대신 "덧셈·비교·대입 같은 기본 연산이 몇 번 일어나는가"를 세면 하드웨어와 무관하게 알고리즘의 본질적 비용을 비교할 수 있다.
- 세 가지 경우:

  - 최선(best case): 가장 운 좋은 입력에서의 횟수(예: 선형 탐색에서 첫 원소가 정답 → `O(1)`).
  - 최악(worst case): 가장 나쁜 입력(정답이 끝에 있거나 없음 → `O(n)`). 코테에서 보증해야 하는 값은 보통 이것.
  - 평균(average case): 입력 분포를 가정한 기댓값.

- 분석 방법: 각 줄이 실행되는 횟수를 세어 더한 뒤, 지배항만 남긴다. "1번 실행되는 대입"은 `O(1)`, "`n`번 도는 반복 안의 `O(1)` 작업"은 `O(n)`.

```python
def linear_search(a, target):     # 입력 크기 n = len(a)
    for i in range(len(a)):       # 최악 n번 반복
        if a[i] == target:        # 각 반복 O(1) 비교
            return i              # 최선: 1번 만에 종료 -> O(1)
    return -1                     # 최악: 끝까지 -> O(n)
```

**그림으로 보기**

- 최선·평균·최악은 **코드가 다른 것이 아니라 입력이 다른 것**이다. 같은 선형 탐색에 정답을 어디에 두느냐만 바꿔 보면 셋이 한 그림에 들어온다.

```text
 linear search , n = 8 ,  '^' = position of the target
 index :  0  1  2  3  4  5  6  7
 array : [.][.][.][.][.][.][.][.]
 best  :  ^                          1 compare       -> O(1)
 avg   :              ^              about n/2       -> O(n)
 worst :                       ^     n compares      -> O(n)
 none  :  (target absent)            n compares      -> O(n)
 -------------------------------------------------------------
 one algorithm , three costs : the input decides which you get
```

- 평균이 `n/2`인데도 `O(n)`인 이유는 앞 레슨의 규칙 그대로다 — **계수 `1/2`는 `c`에 흡수된다.** 즉 평균과 최악은 등급이 같고, 이런 경우 굳이 평균을 따로 말할 이유가 없다.

- 반대로 등급이 갈리는 예도 있다. 정렬된 배열에서 이진탐색은 최선 `O(1)`(가운데가 정답), 최악 `O(log n)`이며, **최악조차 로그**라는 점이 이 알고리즘의 가치다.

**손으로 따라가기**

아래 코드에서 **각 줄이 몇 번 실행되는지** 세어 `T(n)`을 만들고, 마지막에 지배항만 남긴다.

```python
s = 0                          # (1)
for i in range(n):             # (2)
    s += a[i]                  # (3)
best = 0                       # (4)
for i in range(n):             # (5)
    for j in range(n):         # (6)
        if a[i] + a[j] > best: # (7)
            best = a[i] + a[j] # (8)
print(best)                    # (9)
```

| 줄 | 실행 횟수 | 근거 |
|---|---|---|
| (1) | 1 | 대입 한 번 |
| (2) | `n` | 바깥 반복 몸통 진입 횟수 |
| (3) | `n` | (2)마다 1번 |
| (4) | 1 | 대입 한 번 |
| (5) | `n` | 두 번째 바깥 반복 |
| (6) | `n · n = n²` | (5)마다 안쪽이 `n`번 |
| (7) | `n²` | (6)마다 1번 |
| (8) | 0 ~ `n²` | 조건이 참일 때만 |
| (9) | 1 | 출력 한 번 |

- 합: `T(n) = 3 + 2n + 2n²`(최악에는 `+ n²`). **지배항은 `n²`**이므로 `O(n²)`.
- 여기서 두 규칙이 동시에 쓰였다. (2)(3)과 (5)(6)은 **나란히** 있으므로 더하고(`O(n) + O(n²)`), (5)와 (6)은 **중첩**이므로 곱한다(`n × n`). 더한 뒤에는 큰 쪽만 남는다.

이번엔 반대 방향 — **연산 횟수를 실측해 등급을 역산**한다. 같은 문제를 푸는 두 구현의 측정치다.

| `n` | 구현 P | P 배율 | 구현 Q | Q 배율 |
|---|---|---|---|---|
| 1 000 | 10 000 | – | 1 000 000 | – |
| 2 000 | 22 000 | 2.20 | 4 000 000 | 4.00 |
| 4 000 | 48 000 | 2.18 | 16 000 000 | 4.00 |
| 8 000 | 104 000 | 2.17 | 64 000 000 | 4.00 |

- Q는 `n`이 2배일 때 정확히 **4배** → 지수가 2 → `O(n²)`.
- P는 2배보다 **조금 큰 2.2배**가 반복된다 → 순수 선형(`x2`)보다는 무겁고 이차(`x4`)와는 거리가 멀다 → `O(n log n)`. 실제로 `1000 × log₂1000 ≈ 1000 × 10 = 10 000`, `2000 × 11 = 22 000`으로 표와 일치한다.
- 배율이 커질수록 `2.20 → 2.18 → 2.17`로 **천천히 2에 수렴**하는 것도 `n log n`의 특징이다(`log`가 아주 느리게 자라기 때문).

**왜 이렇게 되는가**

- **왜 초(sec)가 아니라 연산 횟수인가**: 같은 코드도 CPU·언어·다른 프로세스 상황에 따라 실행 시간이 몇 배씩 흔들린다. 그래서 이론은 **단위 비용 모델**을 쓴다 — 산술, 비교, 대입, 인덱싱처럼 "크기와 무관하게 일정한 시간이 드는 기본 연산"을 각각 **1**로 세는 것이다. 이 가정 덕분에 `T(n)`이 기계와 무관한 값이 되고, 서로 다른 알고리즘을 종이 위에서 비교할 수 있다.

- **그 모델이 깨지는 자리(가장 중요한 실전 지식)**: 파이썬에서는 "한 줄처럼 보이지만 내부에 반복이 숨은" 연산들이 있다. 이들을 `O(1)`로 세면 분석이 통째로 틀린다.

| 표현 | 겉보기 | 실제 비용 | 이유 |
|---|---|---|---|
| `x in lst` | 한 줄 | `O(n)` | 앞에서부터 전부 비교 |
| `x in st` / `x in dct` | 한 줄 | 평균 `O(1)` | 해시로 바로 찾음 |
| `lst[1:]` | 한 줄 | `O(n)` 시간·공간 | 새 리스트를 복사해 만듦 |
| `s += "a"` (문자열) | 한 줄 | `O(len(s))` | 문자열은 불변이라 매번 새로 만듦 |
| `lst.insert(0, x)` | 한 줄 | `O(n)` | 뒤 원소를 전부 한 칸씩 민다 |
| `lst.append(x)` | 한 줄 | 평균 `O(1)` | 끝에 붙이기만 함 |
| `min(lst)` / `sum(lst)` | 한 줄 | `O(n)` | 전부 훑음 |

  반복문 **안**에 위 왼쪽 열의 연산이 하나라도 들어가면 등급이 한 칸 올라간다(`O(n)` → `O(n²)`). 복잡도 오답의 대부분이 여기서 나온다.

- **왜 기본값이 최악인가**: 우리가 원하는 것은 "**어떤 입력이 와도 이 시간 안에는 끝난다**"는 보증이다. 평균을 말하려면 "입력이 어떤 분포로 들어온다"는 가정이 필요한데, 채점기는 오히려 알고리즘이 가장 싫어하는 입력을 골라 넣는다. 그래서 특별한 언급이 없으면 최악을 답한다.

- **`n`을 무엇으로 정의하느냐가 답을 바꾼다**: 같은 알고리즘도 입력 크기의 정의에 따라 등급이 달라진다. 소수 판정을 `2`부터 `√x`까지 나눠 보는 방법은 **값 `x` 기준으로는 `O(√x)`**지만, 입력이 차지하는 **자릿수 `d` 기준으로는 `x ≈ 10^d`이므로 `O(10^(d/2))` — 지수적**이다. 분석을 시작하기 전에 "여기서 `n`은 무엇인가"를 한 줄로 못 박아야 하는 이유다.

- **최선을 왜 굳이 따지는가**: 최선은 보증이 아니라 **조기 종료가 있는지**를 알려주는 신호다. 최선과 최악이 크게 벌어지면(`O(1)` vs `O(n)`) 입력 순서를 바꾸거나 자주 찾는 값을 앞으로 옮기는 최적화가 의미를 가진다. 반면 둘이 같으면(`O(n)` vs `O(n)`, 예: 전체 합 구하기) 그런 최적화는 무의미하다.

**접근 전략**

- 핵심 아이디어: "입력이 2배가 되면 연산은 몇 배가 되는가?"를 물어라. 2배 → `O(n)`, 4배 → `O(n²)`, 거의 그대로 → `O(log n)`, 완전 불변 → `O(1)`. 이 배율 감각이 복잡도 판정의 지름길이다.
- 전형 절차: (1) 입력 크기 `n`을 정의한다(리스트 길이? 값의 크기? 자릿수?), (2) 지배하는 반복/재귀를 찾는다, (3) 그 안쪽 작업이 `O(1)`인지 확인한다(주의: 파이썬의 `x in list`, 리스트 슬라이싱, `list.insert(0,..)`는 숨은 `O(n)`), (4) 곱해서 지배항을 남긴다.
- 복잡도(주의점): 특별한 말이 없으면 최악의 경우를 답한다. 흔한 실수: 반복 안에서 `in` 연산자(리스트 대상)나 문자열 이어붙이기(`s += ...`)를 `O(1)`로 착각해 실제 `O(n²)`인 코드를 `O(n)`으로 오판하는 것. `n`이 무엇인지 정의하지 않고 분석을 시작하는 것도 잦은 실수다.

**문제**

**1) 최선·최악 나누기** · Easy

- **요구사항**: 정렬 안 된 리스트에서 특정 값을 찾는 선형 탐색이 있다. 이 알고리즘의 최선/최악 시간복잡도를 각각 Big-O로 답하고, 어떤 입력에서 그 경우가 나오는지 한 줄로 서술하라(코드 아님).
- **입력**: 길이 `n` 리스트와 찾을 값
- **출력**: 최선 Big-O, 최악 Big-O, 각 상황 설명
- **예제**: `[5,2,9], target=5` → 최선 `O(1)`(첫 원소가 정답) / `[5,2,9], target=7` → 최악 `O(n)`(끝까지 못 찾음)
- **셀프체크**: 정답이 없을 때가 최악에 포함되는가? 최선이 리스트 길이와 무관하게 상수인가?

```runner
@@SOLUTION

    comps += 1
    if x == target:

(1) 접근·핵심 아이디어

- 선형 탐색을 실제로 돌려 비교 횟수를 세고, 그 결과로 최선/최악을 구분한다. 첫 원소에서 맞으면 비교 1번 → 최선 `O(1)`. 끝까지 못 찾으면 n번 → 최악 `O(n)`. 정답이 없을 때(끝까지 스캔)가 최악에 포함된다.

(2) 코드 단계별

- 첫 줄 리스트, 둘째 줄 target을 읽는다.
- `enumerate`로 앞에서부터 훑으며 비교마다 `comps += 1`. 일치하면 위치를 저장하고 즉시 `break`.
- 찾은 위치가 0이면 best, -1(못 찾음)이면 worst, 그 외면 mid로 라벨링해 비교 횟수와 함께 출력.

(3) 스스로 다시 짤 때 생각 순서

- "정답이 어디 있느냐"가 비용을 결정한다는 점을 먼저 인식한다.
- 맨 앞이면 1번(최선), 맨 뒤이거나 없으면 n번(최악).
- 실제로 세려면 루프마다 카운터를 올리고, 찾는 즉시 멈춘다.
- 최선은 리스트 길이와 무관한 상수, 최악은 길이에 비례함을 결과로 확인.
```

**2) 배율로 복잡도 추정** · Medium

- **요구사항**: 어떤 함수의 실행 연산 횟수를 측정하니 `n=1000`일 때 약 1,000,000회, `n=2000`일 때 약 4,000,000회, `n=4000`일 때 약 16,000,000회였다. 이 알고리즘의 시간복잡도를 Big-O로 추정하고 근거를 적어라.
- **입력**: 위 (n, 연산 횟수) 표
- **출력**: 추정 Big-O와 근거
- **예제**: `n`이 2배(1000→2000) → 횟수 4배 → `O(n²)` / `n` 4배(1000→4000) → 횟수 16배로 일관됨
- **셀프체크**: 2배 입력에 4배 연산이면 지수가 2(제곱)라는 규칙을 적용했는가? `O(n log n)`이었다면 2배에 약 2.2배가 되었을 텐데 그와 구분되는가?

```runner
@@SOLUTION
import sys, math
data = sys.stdin.read().split('\n')
pts = []
```

## L4. 반복문의 시간복잡도

**개념**

- 반복문 기반 알고리즘의 시간복잡도는 "가장 안쪽 기본 연산이 총 몇 번 실행되는가"로 결정된다. 반복의 중첩 깊이와 각 반복 변수의 증가 방식이 핵심이다.
- 분석 규칙:

  - 단일 반복 `for i in range(n)`: 몸통이 `O(1)`이면 전체 `O(n)`.
  - 중첩 반복: 각 반복 횟수를 곱한다. `for i in range(n): for j in range(n)` → `O(n²)`. 안쪽이 `range(m)`이면 `O(n·m)`.
  - 곱셈으로 증가하는 반복 `i *= 2`(또는 `//= 2`): `n`이 절반씩 줄거나 2배씩 늘면 반복 횟수는 `log₂n` → `O(log n)`.
  - 삼각형 반복 `for j in range(i)`: 실행 총합 `0+1+2+...+(n-1) = n(n-1)/2` → 여전히 `O(n²)`(계수 1/2는 지운다).
  - 순차 반복(중첩 아님)은 더한다: `O(n) + O(n) = O(n)`.

```python
# 각 패턴의 총 실행 횟수
for i in range(n):            # O(n)
    work()

for i in range(n):            # O(n^2) : n * n
    for j in range(n):
        work()

for i in range(n):            # O(n^2) : 0+1+...+(n-1) = n(n-1)/2
    for j in range(i):
        work()

i = n
while i > 1:                  # O(log n) : n, n/2, n/4, ... 1
    i //= 2
    work()
```

**그림으로 보기**

- 중첩 반복의 총 실행 횟수는 **몸통이 실행되는 칸의 개수**다. 안쪽 상한이 바깥 변수에 걸리면 그 칸들이 직사각형이 아니라 **삼각형**이 된다.

```text
 for i in range(n):  /  for j in range(i):        ( n = 6 )
 -------------------------------------------------------------
 i = 0 :                       0 runs
 i = 1 : #                     1
 i = 2 : ##                    2
 i = 3 : ###                   3
 i = 4 : ####                  4
 i = 5 : #####                 5
 -------------------------------------------------------------
 total = 0+1+2+3+4+5 = 15 = 6*5/2  ->  n(n-1)/2  ->  O(n^2)
```

- 직사각형(`for j in range(n)`)이면 `n × n`, 삼각형이면 그 절반이다. **절반이어도 등급은 같다** — 계수 `1/2`는 Big-O가 흡수한다. 그래서 "삼각형이니까 더 빠르겠지" 하고 `O(n)`이라 답하면 틀린다.

- 삼각형의 합이 왜 정확히 `n(n+1)/2`인지도 그림으로 끝난다. **같은 삼각형 두 개를 맞물리면 직사각형**이 된다.

```text
 why 1+2+3+4 = 4*5/2      ( two copies make one rectangle )
     S           S flipped          S + S
   # . . . .      . # # # #        # # # # #
   # # . . .      . . # # #        # # # # #
   # # # . .  +   . . . # #   =    # # # # #
   # # # # .      . . . . #        # # # # #
 -------------------------------------------------------------
 2S = 4 rows x 5 cols = 20    ->   S = 10 = 4*5/2
```

- 반복 변수가 `×2` 또는 `÷2`로 움직이면 축의 길이가 `n`이 아니라 `log₂n`이 된다. **눈금이 등간격이 아니라 배수 간격**이기 때문이다.

```text
 halving :  n = 32
    32 -> 16 ->  8 ->  4 ->  2 ->  1
       1     2     3     4     5           = 5 steps
 -------------------------------------------------------------
 after k halvings the size is  n / 2^k
 stop when  n / 2^k = 1   <=>   2^k = n   <=>   k = log2 n
 n = 32 -> 5 ,  n = 1024 -> 10 ,  n = 10^6 -> about 20
```

- 마지막 줄을 외워 두면 감각이 붙는다. **백만짜리 배열도 절반씩 줄이면 20번**이면 끝난다. `O(n)`과 `O(log n)`의 거리는 `10⁶` 대 `20`이다.

**손으로 따라가기**

같은 이중 반복처럼 보이는 네 구조의 총 실행 횟수를 `n = 8`로 직접 센다.

| 구조 | 바깥 횟수 | 안쪽 횟수(각각) | 총 실행(`n=8`) | Big-O |
|---|---|---|---|---|
| `for i in range(n): for j in range(n)` | 8 | 8 | 64 | `O(n²)` |
| `for i in range(n): for j in range(i)` | 8 | 0,1,…,7 | 28 | `O(n²)` |
| `for i in range(n): for j in range(3)` | 8 | 3 | 24 | `O(n)` |
| `for i in range(n): j=n; while j>1: j//=2` | 8 | 3 | 24 | `O(n log n)` |

- 3행과 4행은 `n = 8`에서 **총 실행 횟수가 24로 같지만 등급이 다르다.** 안쪽이 상수 `3`인 3행은 `n`이 커져도 3으로 고정이지만, 4행의 `3`은 `log₂8`이라 `n = 1024`가 되면 10으로 늘어난다. **작은 `n`에서 세는 것만으로는 등급이 안 나온다** — 안쪽 횟수가 `n`의 함수인지 상수인지를 봐야 한다.

`while` 반복의 실제 진행도 한 번 따라가 보자. `i = 20`, `while i > 1: i //= 2`.

| 단계 | 진입 시 `i` | 조건 `i > 1` | `i //= 2` 후 |
|---|---|---|---|
| 1 | 20 | 참 | 10 |
| 2 | 10 | 참 | 5 |
| 3 | 5 | 참 | 2 |
| 4 | 2 | 참 | 1 |
| 5 | 1 | 거짓 → 종료 | – |

- 몸통은 **4번** 실행됐다. `log₂20 ≈ 4.32`이고 정수 나눗셈이 내림이라 `⌊log₂20⌋ = 4`와 일치한다. 이렇게 `+1`/`-1`의 오차가 생겨도 Big-O는 `O(log n)`으로 같다.

**왜 이렇게 되는가**

- **`1+2+…+n = n(n+1)/2`의 유도(가우스 짝짓기)**: 합을 앞에서부터 한 번, 뒤에서부터 한 번 써서 세로로 더한다.

  - `S = 1 + 2 + 3 + … + n`
  - `S = n + (n-1) + (n-2) + … + 1`
  - 세로로 더하면 각 자리가 모두 `n+1`이고, 그런 자리가 `n`개다. 즉 `2S = n(n+1)`이므로 `S = n(n+1)/2`.

  전개하면 `n²/2 + n/2`이고, 지배항 `n²/2`에서 계수를 떼면 **`O(n²)`**이다. 위 그림의 "삼각형 두 개 = 직사각형"이 정확히 이 계산의 그림 버전이다.

- **절반씩 줄면 왜 `log₂n`번인가**: 크기 `n`에서 시작해 `k`번 반으로 줄이면 남는 크기는 `n / 2^k`다. 반복은 크기가 1 이하가 될 때 멈추므로 종료 조건은 `n / 2^k ≤ 1`, 즉 **`2^k ≥ n`**이다. 양변에 밑이 2인 로그를 취하면 `k ≥ log₂n`. 이 부등식을 만족하는 가장 작은 `k`가 반복 횟수이고, 그래서 `O(log n)`이다. 거꾸로 `×2`씩 늘리는 반복(`i = 1; while i < n: i *= 2`)도 같은 식이라 횟수가 같다.

- **중첩이 곱이 되는 이유**: 바깥이 한 바퀴 돌 때마다 안쪽 반복이 **처음부터 끝까지 통째로** 실행된다. 바깥 `A`번, 안쪽 매번 `B`번이면 몸통은 `A × B`번이다. 반대로 두 반복이 **나란히** 있으면 하나가 끝난 뒤 다른 하나가 시작하므로 `A + B`번이고, 합은 큰 쪽에 흡수된다. "곱이냐 합이냐"는 들여쓰기 한 칸으로 갈린다.

- **안쪽 상한이 바깥 변수에 걸릴 때는 곱이 아니라 합**: `for j in range(i)`처럼 안쪽 횟수가 매번 달라지면 `n × n`으로 곱할 수 없고, `Σᵢ i`처럼 **더해야** 정확하다. 다만 등차수열의 합은 `n²/2`라 결과 등급은 여전히 `O(n²)`다. 등급만 필요하면 "안쪽이 최대 `n`번이니 상한 `n²`"으로 잡아도 같은 답이 나온다.

- **정확한 합이 등급을 바꾸는 경우도 있다**: `for i in range(1, n): for j in range(i, n, i)`처럼 안쪽 횟수가 `n/i`이면 총합은 `n/1 + n/2 + n/3 + … + n/n = n(1 + 1/2 + … + 1/n)`이다. 괄호 안은 조화급수로 대략 `ln n`이므로 전체는 **`O(n log n)`** — 이중 반복인데 `O(n²)`이 아니다. "이중 반복 = `n²`"이라는 반사적 판단이 틀리는 대표 사례이며, 이런 구조는 배수 순회(체 알고리즘)에서 흔히 나온다.

- **`break`가 있으면**: 최악을 답해야 하므로 "`break`가 한 번도 안 걸리는 입력"을 가정해 상한을 잡는다. 평균적으로 절반에서 끊긴다 해도 계수 `1/2`는 흡수되므로 등급은 그대로다. `break`가 등급을 바꾸는 경우는 "반복 횟수 자체가 `n`에 무관해질 때"뿐이다(예: 최대 3번 돌고 반드시 탈출 → `O(1)`).

- **내장 함수는 반복이다**: `for` 안에 `sorted(...)`, `min(a[i:])`, `sum(...)`, `x in lst`가 있으면 그 줄이 이미 `O(n log n)` 또는 `O(n)`짜리 반복이다. 겉으로 반복이 한 겹처럼 보여도 실제로는 두 겹이므로, 반복문 분석에서는 **"이 줄 안에 숨은 반복이 있는가"를 매번 확인**해야 한다.

**접근 전략**

- 핵심 아이디어: "반복 변수가 어떻게 변하는가"를 본다. `+1`씩 늘면 그 축은 `n`(선형), `×2`/`÷2`면 `log n`. 그다음 중첩된 축들을 곱하고, 나란히 있는 블록은 더한 뒤 지배항만 남긴다.
- 전형 절차: (1) 안쪽에서 바깥쪽으로 각 반복의 실행 횟수를 식으로 적는다, (2) 중첩은 곱·순차는 합, (3) `break`/`return`이 있으면 최악 기준으로 "안 걸리는 경우"를 상한으로 잡는다, (4) 계수·저차항 제거.
- 복잡도(주의점): 안쪽 반복 상한이 바깥 변수 `i`에 의존하면(`range(i)`) 곱이 아니라 등차합으로 계산해야 정확하다(그래도 `O(n²)`). 흔한 실수: 이중 반복이라고 무조건 `O(n²)`로 단정하는 것 — 안쪽이 `log n`번이면 `O(n log n)`이다. 또 반복 안의 파이썬 내장 호출(`sorted`, `min` over slice)이 숨은 반복을 품고 있는지 확인해야 한다.

**문제**

**1) 중첩 반복 판정** · Easy

```runner
@@EXPL
(1) 접근·핵심 아이디어

- 세 반복 구조의 안쪽 기본 연산 총 실행 횟수를 정확히 계산한다. (a) 완전 이중 반복 → n*n = `O(n^2)`. (b) 삼각형 반복(j가 0..i) → `0+1+...+(n-1)=n(n-1)/2` = `O(n^2)`. (c) 매번 절반(`//2`)으로 줄이므로 `log2 n`번 = `O(log n)`.

(2) 코드 단계별

- 입력 `kind n`(예: `a 4`)을 읽는다.
- a는 `n*n`, b는 삼각수 `n(n-1)/2`를 공식으로 바로 계산.
- c는 개념 코드처럼 `while i>1: i//=2`를 돌려 실제 반복 횟수를 세어 `log2 n`을 재현. n=8이면 8→4→2→1로 3번.

(3) 스스로 다시 짤 때 생각 순서

- 반복 변수가 `+1`로 늘면 그 축은 n(선형), `//2`면 log n임을 먼저 판별.
- 중첩은 각 축의 횟수를 곱한다(a).
- 안쪽 상한이 바깥 i에 의존하면 곱이 아니라 등차합으로(b) → 여전히 `O(n^2)`.
- 절반씩 줄면 log n번, 계수·저차항은 버리고 등급만 답.
```

**2) 소수 판정 비용** · Medium

- **요구사항**: 정수 `x`가 소수인지 `2`부터 `√x`까지 나눠보며 판정하는 방법의 시간복잡도를, 입력 크기를 "값 `x`" 기준과 "자릿수 `d`" 기준 두 가지로 각각 논하라. `x` 하나 판정만 고려한다.
- **입력**: 정수 `x`
- **출력**: 값 기준 Big-O, 자릿수 기준과의 관계 서술
- **예제**: `x=97` → `2..9`까지 8번 검사(√97≈9.8) / `x=100` → `2..10`까지 검사
- **셀프체크**: 값 `x` 기준으로 반복이 약 `√x`번이라 `O(√x)`인가? 이것이 자릿수로 보면 왜 지수적으로 보이는지(값이 자릿수의 지수) 짚었는가?

```runner
@@SOLUTION
import sys
x = int(sys.stdin.readline())
checks = 0
is_prime = True
if x < 2:
    is_prime = False
else:
    d = 2
    while d * d <= x:
        checks += 1
        if x % d == 0:
            is_prime = False
            break
        d += 1
print('prime' if is_prime else 'composite', checks)
@@TESTS
--IN
97
--OUT
prime 8
--IN
100
--OUT
composite 1
@@EXPL
(1) 접근·핵심 아이디어

- `2`부터 `sqrt(x)`까지만 나눠보면 소수 판정이 충분하다(약수는 sqrt를 기준으로 대칭). 값 `x` 기준으로 반복은 약 `sqrt(x)`번이라 `O(sqrt x)`. 자릿수 `d` 기준으로 보면 `x ≈ 10^d`이라 `sqrt(x) = 10^(d/2)` → 자릿수 대비 지수적으로 커진다.

(2) 코드 단계별

- 정수 x를 읽고, 2 미만이면 소수 아님.
- `d*d <= x` 동안 나눠보며 검사 횟수를 센다. 나누어떨어지면 합성수 판정 후 중단.
- 결과(prime/composite)와 실제 검사 횟수를 출력. x=97은 d=2..9로 8번 검사 후 소수, x=100은 d=2에서 바로 걸려 1번.

(3) 스스로 다시 짤 때 생각 순서

- 약수는 sqrt(x)에서 짝을 이루므로 sqrt까지만 보면 된다는 사실을 먼저 확인.
- 반복 조건을 `d*d <= x`로 두면 부동소수 sqrt 없이 정확하다.
- 반복 횟수가 약 sqrt(x)이므로 값 기준 `O(sqrt x)`.
- 입력 크기를 자릿수 d로 재정의하면 값=10^d이라 같은 비용이 지수적으로 보임을 짚는다.
```

**3) 부분합이 목표가 되는 쌍 세기** · Medium

- **요구사항**: 길이 `n` 리스트에서 두 원소의 합이 `target`이 되는 (순서 무관) 쌍의 개수를 세려 한다. (a) 모든 쌍을 이중 반복으로 검사하는 방법의 복잡도, (b) `set`/`dict`로 한 번 훑어 개선했을 때의 복잡도를 구하라(구현은 하지 말고 복잡도와 아이디어만).
- **입력**: 리스트 `a`, 정수 `target`
- **출력**: (a)(b) 각각의 시간복잡도와 (b)의 핵심 아이디어 한 줄
- **예제**: `a=[1,2,3,4], target=5` → 쌍 `(1,4),(2,3)` 2개 / `a=[1,1,1], target=2` → 쌍 3개
- **셀프체크**: (a)가 쌍의 수 `n(n-1)/2` → `O(n²)`인가? (b)에서 "각 `x`마다 `target-x`가 이미 나왔는지 `set`으로 확인"하면 한 번 훑어 `O(n)`이 되는가? 중복 값·`x==target-x` 경계를 어떻게 셀지 고민했는가?

```runner
@@SOLUTION
import sys
from collections import Counter
data = sys.stdin.read().split('\n')
a = list(map(int, data[0].split())) if data[0].strip() else []
target = int(data[1])
cnt = Counter()
pairs = 0
for x in a:
    pairs += cnt[target - x]
    cnt[x] += 1
print(pairs)
@@TESTS
--IN
1 2 3 4
5
--OUT
2
--IN
1 1 1
2
--OUT
3
@@EXPL
**이 풀이의 새 문법**

- `collections.Counter`: 값의 등장 횟수를 세는 dict의 특수 버전. 일반 dict와 달리 없는 키를 조회해도 에러 없이 0을 돌려준다(예: `cnt[target-x]`가 처음이면 0).

(1) 접근·핵심 아이디어

- (a) 모든 쌍을 이중 반복으로 검사하면 쌍의 수가 `n(n-1)/2`라 `O(n^2)`. (b) 한 번만 훑으면서 각 원소 `x`에서 "지금까지 본 값 중 `target-x`가 몇 개였나"를 `dict`(여기선 `Counter`)로 즉시 조회하면 평균 `O(1)`, 전체 `O(n)`이다. 핵심 아이디어: 각 `x`를 오른쪽 원소로 보고, 그 짝 `target-x`가 이미 왼쪽에 몇 번 나왔는지 세어 누적한다.

(2) 코드 단계별

- 리스트 `a`와 `target`을 읽는다.
- `x`를 순서대로 보며 먼저 `cnt[target-x]`(이미 본 짝의 개수)를 답에 더하고, 그다음 `cnt[x]`를 1 늘린다. 더하기 전에 세므로 자기 자신과 짝지어지는 중복 계산이 없다.
- `[1,2,3,4] target=5`: 4를 볼 때 1이 이미 있어 +1, 3을 볼 때 2가 이미 있어 +1 → 총 2. `[1,1,1] target=2`: 둘째 1에서 +1, 셋째 1에서 앞의 1이 둘이라 +2 → 총 3.

(3) 스스로 다시 짤 때 생각 순서

- 순진한 방법(모든 쌍 이중 반복)의 비용 `n(n-1)/2 = O(n^2)`를 먼저 인식한다.
- "각 x의 짝은 target-x 하나로 정해진다"는 점을 이용해 탐색을 조회로 바꾼다.
- 왼쪽에서 이미 본 값들을 카운터에 쌓고, 새 x마다 짝의 개수를 더한 뒤 자신을 등록 — 더한 뒤 등록 순서가 중복·자기짝 경계를 자연히 처리.
- set/dict 멤버십이 평균 O(1)이라 한 번 훑는 O(n)으로 떨어짐을 확인.
```


## L5. 재귀함수의 시간복잡도

**개념**

- 재귀 알고리즘의 시간복잡도는 "재귀 호출이 만드는 호출 트리의 전체 작업량"이다. 반복문처럼 눈으로 곱하기 어려우므로, 점화식(recurrence relation) `T(n) = (자기 자신 호출들) + (합치는 비용)`을 세워 푼다.
- 두 가지 대표 패턴:

  - 크기를 1씩 줄이며 1번 호출: `T(n)=T(n-1)+O(1)` → 호출이 `n`번 → `O(n)`(예: 재귀 팩토리얼). 합치는 비용이 `O(n)`이면 `T(n)=T(n-1)+O(n)` → `O(n²)`.
  - 크기를 절반으로 줄이며 호출:

    - 1번만 호출 `T(n)=T(n/2)+O(1)` → `O(log n)`(예: 이진탐색).
    - 2번 호출 + 선형 병합 `T(n)=2T(n/2)+O(n)` → `O(n log n)`(예: 병합 정렬).
    - 2번 호출 + 상수 `T(n)=2T(n/2)+O(1)` → `O(n)`.

- 겹치는 부분문제: 나이브 피보나치 `T(n)=T(n-1)+T(n-2)+O(1)`는 호출 수가 지수적으로 폭발 → `O(2ⁿ)`에 가깝다(정확히는 약 `1.618ⁿ`이지만 `O(2ⁿ)`로 이해하면 충분). 같은 값을 반복 계산하기 때문이며, 메모이제이션(Ch8)으로 `O(n)`까지 줄일 수 있다.

```python
def fib(n):                # T(n) = T(n-1) + T(n-2) + O(1)
    if n < 2:              # 기저 조건
        return n
    return fib(n-1) + fib(n-2)   # 같은 부분문제 중복 계산 -> 지수적

def bsearch(a, lo, hi, x):        # T(n) = T(n/2) + O(1) -> O(log n)
    if lo > hi:
        return -1
    mid = (lo + hi) // 2
    if a[mid] == x: return mid
    if a[mid] < x:  return bsearch(a, mid+1, hi, x)
    else:           return bsearch(a, lo, mid-1, x)
```

**그림으로 보기**

- 재귀 비용은 **호출 트리의 노드 수**다. 가지가 2개인데 크기가 `1`씩만 줄면, 깊이가 `n`까지 가면서 노드가 층마다 2배로 불어난다.

```text
 T(n) = 2 T(n-1) + 1     ( branch 2 , size shrinks by 1 )
 -------------------------------------------------------------
 Lv0                    *                       1 node
 Lv1              *           *                 2
 Lv2           *     *     *     *              4
 Lv3         *  *   *  *  *  *   *  *           8
  :             ... depth n ...                 2^k
 -------------------------------------------------------------
 total = 1 + 2 + 4 + ... + 2^(n-1) = 2^n - 1     ->  O(2^n)
```

- 같은 "가지 2개"라도 크기가 **절반**으로 줄면 이야기가 완전히 달라진다. 깊이가 `n`이 아니라 `log n`이 되어 노드 수가 `2^(log n) = n`으로 주저앉기 때문이다. **분기 수보다 크기 감소 방식이 훨씬 세다.**

- 점화식을 푸는 정석은 **레벨별 작업량을 더한 수열의 모양**을 보는 것이다. 세 가지 모양밖에 없다.

```text
 level sums of  T(n) = a T(n/b) + f(n)
 -------------------------------------------------------------
 2T(n/2) + n :   n    n    n    n    n      flat     -> n log n
 1T(n/2) + n :   n   n/2  n/4  n/8  ...     top      -> 2n = O(n)
 2T(n/2) + 1 :   1    2    4    8  ...  n   bottom   -> 2n = O(n)
 -------------------------------------------------------------
 flat   : every level costs the same -> multiply by log n levels
 top    : geometric going down -> the root term dominates
 bottom : geometric going up   -> the leaves dominate
```

- 이 그림 하나로 "왜 병합 정렬은 `n log n`인데 이진탐색은 `log n`이고, 가지가 2개인 `2T(n/2)+O(1)`은 `O(n)`인가"가 전부 설명된다. **레벨 합이 평평하면 곱하고, 한쪽으로 기울면 그쪽 끝만 남는다.**

**손으로 따라가기**

`fib(5)`의 호출 트리를 전부 펼쳐 **같은 값이 몇 번 다시 계산되는지** 센다.

```text
 fib(5) call tree
                       f5
                  /          \
                f4            f3
              /    \         /    \
            f3      f2      f2     f1
           /  \    /  \    /  \
         f2    f1 f1    f0 f1   f0
        /  \
      f1    f0
```

| 값 | 호출 횟수 | 어디서 불리는가 |
|---|---|---|
| `fib(5)` | 1 | 최초 호출 |
| `fib(4)` | 1 | `fib(5)`에서 |
| `fib(3)` | 2 | `fib(5)`에서 1번 + `fib(4)`에서 1번 |
| `fib(2)` | 3 | `fib(4)` 1번 + `fib(3)` 2개가 각 1번 |
| `fib(1)` | 5 | `fib(3)` 2개 + `fib(2)` 3개 |
| `fib(0)` | 3 | `fib(2)` 3개가 각 1번 |

- 노드 총합 **15개**. 답 `fib(5) = 5`를 얻으려고 15번을 호출한 것이다. `n = 30`이면 노드가 260만 개를 넘고, `n = 40`이면 3억 개를 넘는다 — 이것이 지수 폭발의 실제 체감이다.
- 규칙성도 보인다. 총 노드 수는 `2·fib(n+1) − 1`이다(`n = 5`면 `2·8 − 1 = 15`).

이번엔 하노이 탑 점화식 `M(n) = 2M(n-1) + 1`, `M(1) = 1`을 **반복 대입법**으로 직접 푼다.

| 대입 횟수 | 식 | 정리하면 |
|---|---|---|
| 0 | `M(n)` | – |
| 1 | `2M(n-1) + 1` | `2¹·M(n-1) + 1` |
| 2 | `2(2M(n-2)+1) + 1` | `2²·M(n-2) + 3` |
| 3 | `2(4M(n-3)+3) + 1` | `2³·M(n-3) + 7` |
| `k` | – | `2^k·M(n-k) + (2^k − 1)` |
| `k = n-1` | `2^(n-1)·M(1) + 2^(n-1) − 1` | `2^(n-1) + 2^(n-1) − 1 = 2ⁿ − 1` |

- 닫힌 식 `M(n) = 2ⁿ − 1`. 검산: `n=1 → 1`, `n=3 → 7`, `n=4 → 15`. 따라서 `O(2ⁿ)`.
- 패턴을 보라 — `k`번 대입하면 앞 계수가 `2^k`, 뒤에 붙는 상수가 `2^k − 1`이다. **`k`를 기저에 닿는 값(`n-1`)으로 두는 순간 답이 나온다.** 이것이 점화식을 푸는 가장 기본적인 도구다.

**왜 이렇게 되는가**

- **점화식은 세 가지만 읽으면 세워진다**: (1) 한 번의 호출이 자기 자신을 **몇 번** 부르는가(분기 수 `a`), (2) 문제 크기가 **어떻게** 줄어드는가(`n-1`인가 `n/b`인가), (3) 호출을 빼고 그 함수가 스스로 하는 일의 비용은 얼마인가(`f(n)`). 이 셋을 `T(n) = a·T(작아진 크기) + f(n)` 자리에 그대로 끼우면 된다. 기저 조건(`T(1)`)도 반드시 함께 적는다 — 없으면 식이 닫히지 않는다.

- **반복 대입법(unrolling)의 절차**: 오른쪽의 `T(...)`를 정의로 한 번 더 바꿔 쓰기를 반복해 규칙을 찾고, 기저에 닿는 `k`를 대입해 마무리한다. 위 하노이 표가 그 전 과정이다. `-1`씩 줄면 `k = n-1`에서, `/2`씩 줄면 **`n/2^k = 1` 즉 `k = log₂n`**에서 기저에 닿는다.

- **네 가지 대표 결론을 각각 유도하면**:

  - `T(n) = T(n-1) + O(1)`: 크기가 1씩 줄며 한 줄로 내려가므로 호출이 `n`개, 각 `O(1)` → **`O(n)`**.
  - `T(n) = T(n-1) + O(n)`: 같은 `n`개의 호출이지만 각 단계 비용이 `n, n-1, …, 1` → 합이 `n(n+1)/2` → **`O(n²)`**. (앞 레슨의 삼각형과 똑같은 합이다.)
  - `T(n) = T(n/2) + O(1)`: 크기가 절반씩이라 깊이가 `log₂n`, 각 `O(1)` → **`O(log n)`**.
  - `T(n) = 2T(n/2) + O(n)`: 레벨 `k`에는 노드가 `2^k`개, 각 크기가 `n/2^k`이므로 레벨 합이 항상 `2^k × n/2^k = n`. 레벨이 `log n`개 → **`O(n log n)`**.

- **등비급수가 상수 배로 접히는 이유**: `T(n) = T(n/2) + O(n)`의 레벨 합은 `n + n/2 + n/4 + …`이다. 이 합은 `n × (1 + 1/2 + 1/4 + …) < 2n`이므로 **`O(n)`** — 무한히 더해도 첫 항의 2배를 못 넘는다. 반대로 `2T(n/2)+O(1)`은 `1 + 2 + 4 + … + n < 2n`이라 역시 `O(n)`인데, 이번엔 **마지막 항(잎)이 전부를 지배**한다. 등비수열은 공비가 1보다 작으면 첫 항이, 크면 마지막 항이 답을 정한다.

- **나이브 피보나치가 지수적인 이유(하한까지)**: `T(n) = T(n-1) + T(n-2) + O(1)`에서 `T(n-1) ≥ T(n-2)`이므로 `T(n) ≥ 2T(n-2)`다. 이를 반복 대입하면 `T(n) ≥ 2^(n/2)`, 즉 **적어도 지수적**임이 증명된다. 위쪽으로는 `T(n) ≤ 2T(n-1)`에서 `T(n) ≤ 2ⁿ`이므로 `2^(n/2) ≤ T(n) ≤ 2ⁿ`. 실제 값은 `≈ 1.618ⁿ`(황금비)이지만, 코테에서는 **"지수라서 못 쓴다"**만 알면 충분하다.

- **메모이제이션이 왜 `O(n)`으로 떨어지는가 — 가장 중요한 일반 원리**: 재귀에 메모를 붙이면 비용이 다음 곱으로 바뀐다.

  - **서로 다른 부분문제의 개수(상태 수) × 부분문제 하나를 푸는 비용(전이 비용)**

  피보나치의 상태는 `fib(0) … fib(n)`으로 `n+1`개뿐이고, 각각을 계산하는 데 덧셈 한 번(`O(1)`)이 든다. 따라서 `O(n)`. 나이브 재귀가 느린 것은 **상태가 많아서가 아니라 같은 상태를 몇 번이고 다시 방문해서**다. 이 "상태 수 × 전이 비용" 공식은 이후 DP 챕터의 복잡도 계산을 그대로 지배한다.

- **재귀 분석에서 자주 어긋나는 지점**: (1) 크기 감소가 `-1`인지 `/2`인지 착각하는 것 — 깊이가 `n`이냐 `log n`이냐가 여기서 갈린다. (2) 호출 밖 비용 `f(n)`을 빼먹는 것 — 슬라이싱 `a[:mid]`로 배열을 잘라 넘기면 그 자체가 `O(n)`이라 `2T(n/2)+O(1)`이 아니라 `2T(n/2)+O(n)`이 된다. (3) 형제 호출을 "동시에 살아 있는 것"으로 착각하는 것 — 시간은 더하지만 **공간은 더하지 않는다**(다음 레슨).

**접근 전략**

- 핵심 아이디어: (1) 한 번의 호출이 자기 자신을 몇 번 부르는가(분기 수), (2) 매번 문제 크기가 얼마나 줄어드는가(`-1`인가 `/2`인가), (3) 호출 밖에서 드는 일(병합/반복) 비용은 얼마인가 — 이 셋으로 점화식을 세운다. 그다음 "호출 트리의 깊이 × 각 레벨의 총 작업량"으로 직관적으로 합산한다.
- 재귀 트리로 보는 `T(n)=2T(n/2)+O(n)`(병합 정렬): 각 레벨의 총 작업량은 `n`으로 일정하고(레벨0은 `n` 하나, 레벨1은 `n/2` 두 개=`n`, 레벨2는 `n/4` 네 개=`n` …), 크기가 매번 절반이라 레벨 수가 `log n`이다. 따라서 총합 = 레벨별 작업량 `n` × 레벨 수 `log n` = `O(n log n)`.

```text
Lv0 :            [  n  ]                 sum = n
Lv1 :        [ n/2 ][ n/2 ]              sum = n
Lv2 :    [n/4][n/4][n/4][n/4]            sum = n
 :         ... halving, log n levels ...
-------------------------------------------------
   n per level  x  log n levels  =  n log n
```
- 대표 결론 암기: `T(n)=T(n-1)+O(1)→O(n)`, `T(n)=T(n/2)+O(1)→O(log n)`, `T(n)=2T(n/2)+O(n)→O(n log n)`, `T(n)=2T(n-1)+O(1)→O(2ⁿ)`. 이 네 개만 알면 대부분 판별된다.
- 복잡도(주의점): 재귀는 시간뿐 아니라 호출 스택 깊이만큼 공간도 먹는다(다음 레슨). 흔한 실수: 나이브 피보나치처럼 "부분문제 중복"을 못 보고 `O(n)`이라 오판하는 것, 그리고 `/2`로 줄어드는데 `-1`로 착각해 `O(n)`을 `O(log n)`으로 혹은 반대로 잘못 세는 것. 기저 조건 누락은 복잡도가 아니라 아예 무한 재귀(스택 오버플로)를 부른다.

**문제**

**1) 점화식에서 복잡도 뽑기** · Easy

```runner
(1) 접근·핵심 아이디어

- 각 점화식을 "분기 수 × 크기 감소 방식 × 호출 밖 비용"으로 읽는다. (a) `T(n)=T(n-1)+O(1)`: 크기를 1씩 줄이며 1번 호출 → 호출 n번 → `O(n)`. (b) `T(n)=T(n/2)+O(1)`: 절반으로 줄이며 1번 호출 → 깊이 `log n` → `O(log n)`. (c) `T(n)=2T(n/2)+O(n)`: 각 레벨의 총 작업량이 `O(n)`으로 일정하고 레벨이 `log n`개 → `O(n log n)`(병합 정렬).

(2) 코드 단계별

- 세 점화식의 결론을 딕셔너리로 표화(a→O(n), b→O(log n), c→O(n log n)).
- 입력으로 들어온 라벨(`a`/`b`/`c`)마다 대응 Big-O를 순서대로 출력.
- 손 분석이 본질이므로 코드는 분석 결과를 조회하는 룩업이다.

(3) 스스로 다시 짤 때 생각 순서

- 점화식에서 (1) 자기 자신 호출 횟수(분기), (2) 크기 감소가 `-1`인지 `/2`인지, (3) 호출 밖 결합 비용 세 가지를 뽑는다.
- `-1`+1번 호출이면 깊이 n → O(n), `/2`+1번이면 깊이 log n → O(log n).
- `2T(n/2)+O(n)`은 재귀 트리에서 레벨당 n × 레벨 수 log n = n log n.
- 대표 결론 네 개(O(n), O(log n), O(n log n), O(2^n))에 대응시키면 대부분 판별된다.
```

**2) 나이브 피보나치의 함정** · Medium

- **요구사항**: 재귀로 `fib(n)=fib(n-1)+fib(n-2)`를 계산할 때 (a) 시간복잡도가 왜 다항식이 아니라 지수적인지 점화식과 호출 트리로 설명하고, (b) `fib(5)`를 계산할 때 `fib(2)`가 몇 번 호출되는지 실제로 세어라(코드 실행 없이 트리로).
- **입력**: 정수 `n`
- **출력**: (a) 지수적 근거, (b) `fib(5)`에서 `fib(2)` 호출 횟수
- **예제**: 호출 트리 `fib(5)→fib(4),fib(3)` ... 전개 시 `fib(2)`는 `3`번 호출 / `fib(0)`은 `2`번, `fib(1)`은 `5`번 호출
- **셀프체크**: `fib(5)` 트리에서 `fib(3)`이 2번, 각 `fib(3)`이 `fib(2)`를 1번, 그리고 `fib(4)`가 직접 `fib(2)`를 1번 불러 총 `2+1=3`번인지 손으로 확인했는가? 중복 계산이 지수 폭발의 원인임을 짚었는가?

```runner
(2) 코드 단계별

- `fib`가 호출될 때마다 `counts[k]`를 1 증가시켜 각 인자가 몇 번 불렸는지 집계.
- `fib(n)`을 한 번 돌린 뒤 `counts[2]`를 출력 → `fib(n)`에서 `fib(2)`가 불린 횟수.
- `fib(5)`: `fib(4)`가 직접 1번 + `fib(3)`이 2번 등장하며 각기 1번 → 총 3번(예제 일치). `fib(6)`이면 5번(중복이 더 커짐).

(3) 스스로 다시 짤 때 생각 순서

- 한 호출이 두 갈래로 갈라지고 크기가 1씩만 줄면 트리 노드가 지수적으로 는다는 점을 먼저 그린다.
- 같은 부분문제가 여러 번 나타남을 확인하려면 인자별 호출 횟수를 딕셔너리로 기록한다.
- 호출부에 카운터 증가 한 줄만 넣고 나머지는 정의 그대로 재귀.
- `fib(2)` 호출 수가 `fib(n-1)`과 같아짐(fib(5)→3=fib(4), fib(6)→5=fib(5))을 관찰하면 중복 구조가 보인다.
```

**3) 하노이 탑 이동 횟수** · Medium

- **예제**: `n=3` → `M=7` / `n=4` → `M=15`
- **셀프체크**: `M(n)=2ⁿ-1`인가?(`n=3`이면 `2³-1=7` 검산) 호출이 매번 2갈래로 `n`까지 내려가므로 `O(2ⁿ)`인가?

```runner
(1) 접근·핵심 아이디어

- 매 단계 2배로 커지므로 시간복잡도 `O(2^n)`. 실제 이동을 재귀로 시뮬레이션해도 되지만 개수만 필요하면 닫힌 식이 즉답.
```

## L6. 공간복잡도

**개념**

- 공간복잡도(space complexity)는 입력 크기 `n`에 대해 알고리즘이 추가로 사용하는 메모리 양을 함수로 나타낸 것이다. 시간처럼 Big-O로 표현하며, 보통 입력 자체를 저장하는 공간은 빼고 "추가로 쓰는(auxiliary) 공간"을 센다.
- 무엇을 세는가:

  - 변수·누적기: 몇 개든 상수 개면 `O(1)`.
  - 보조 자료구조: 크기 `n` 리스트/집합/딕셔너리를 만들면 `O(n)`, `n×n` 2차원 배열이면 `O(n²)`.
  - 재귀 호출 스택: 동시에 쌓이는 프레임의 최대 깊이만큼. 깊이 `n`이면 `O(n)`, `log n`이면 `O(log n)`.

- 시간-공간 트레이드오프: 메모(캐시)를 써서 시간을 줄이면 공간이 늘고, 제자리(in-place) 알고리즘으로 공간을 아끼면 코드가 복잡해진다. 둘 중 무엇이 병목인지에 따라 선택한다.

```python
def sum_iter(a):          # 공간 O(1): 누적 변수 하나만 사용
    s = 0
    for x in a:
        s += x
    return s

def build_prefix(a):      # 공간 O(n): 길이 n 결과 리스트 생성
    out = [0] * (len(a)+1)
    for i, x in enumerate(a):
        out[i+1] = out[i] + x
    return out

def rec_sum(a, i=0):      # 시간 O(n), 공간 O(n): 재귀 스택 깊이 n
    if i == len(a): return 0
    return a[i] + rec_sum(a, i+1)
```

**그림으로 보기**

- 재귀의 공간은 **가장 깊게 쌓였을 때의 스택 높이**다. 크기를 `1`씩 줄이면 높이가 `n`, 절반씩 줄이면 `log n`이다. 시간이 같아도 공간은 이렇게 갈린다.

```text
 the call stack at its deepest moment
   rec_sum(a, 0) , n = 4           bsearch , n = 8
   +-----------+                   +-----------+
   |   i = 3   | <- top            |  level 2  | <- top
   +-----------+                   +-----------+
   |   i = 2   |                   |  level 1  |
   +-----------+                   +-----------+
   |   i = 1   |                   |  level 0  |
   +-----------+                   +-----------+
   |   i = 0   | <- bottom         depth = log2 8 = 3
   +-----------+                   space  O(log n)
   depth = n = 4
   space  O(n)
```

- 시간과 공간을 헷갈리게 만드는 지점은 **형제 호출**이다. 병합 정렬은 호출을 15번 하지만, 그 15개가 동시에 스택에 있는 것은 아니다. 왼쪽 가지가 **끝나서 사라진 뒤에** 오른쪽 가지가 시작한다.

```text
 mergesort(n=8) : 15 calls in total , but how many are alive ?
                    [ 8 ]                 <- alive
                  /       \
              [ 4 ]         [ 4 ]         left finishes first
             /     \       /     \
          [2]     [2]   [2]     [2]       right starts after
 -------------------------------------------------------------
 alive frames = one root-to-leaf path = log n + 1 = 4
 a finished sibling has already been popped   # 동시에 안 쌓인다
```

- 그래서 **시간은 트리 전체 노드 수, 공간은 트리의 높이**다. 같은 트리에서 두 값을 다르게 읽는 것이 재귀 분석의 핵심 감각이다.

**손으로 따라가기**

`rec_sum([4, 7, 2])`를 push/pop 순서대로 따라가며 **최대 깊이**를 잰다.

| 시각 | 동작 | 스택(아래 → 위) | 깊이 |
|---|---|---|---|
| 1 | `rec_sum(i=0)` 호출 | `i0` | 1 |
| 2 | `rec_sum(i=1)` 호출 | `i0, i1` | 2 |
| 3 | `rec_sum(i=2)` 호출 | `i0, i1, i2` | 3 |
| 4 | `rec_sum(i=3)` 호출 → 기저 | `i0, i1, i2, i3` | **4 (최대)** |
| 5 | `i3` 이 `0` 반환 | `i0, i1, i2` | 3 |
| 6 | `i2` 가 `2+0=2` 반환 | `i0, i1` | 2 |
| 7 | `i1` 이 `7+2=9` 반환 | `i0` | 1 |
| 8 | `i0` 이 `4+9=13` 반환 | (빈 스택) | 0 |

- 답 `13`, 최대 깊이 `n+1 = 4` → 공간 `O(n)`. **덧셈이 실제로 일어나는 시점(5~8)은 전부 "돌아오는 길"**이고, 그 전까지는 아무것도 계산되지 않은 채 프레임만 쌓인다. 이것이 재귀가 메모리를 먹는 이유다.
- 같은 합을 `for` 반복으로 구하면 변수 `s` 하나뿐이라 깊이가 항상 1 → 공간 `O(1)`. **시간은 둘 다 `O(n)`이지만 공간은 `O(n)` 대 `O(1)`**이다.

세 가지 구현의 시간·공간을 나란히 놓으면 트레이드오프가 한눈에 보인다.

| 구현 | 시간 | 공간(보조) | 메모 |
|---|---|---|---|
| 나이브 재귀 피보나치 | `O(2ⁿ)` | `O(n)` | 스택 깊이만 |
| 메모이제이션 재귀 | `O(n)` | `O(n)` | 메모 표 + 스택 |
| 아래에서 위로 두 변수만 | `O(n)` | `O(1)` | `prev`, `cur` 두 개 |

- 위→아래 한 칸씩 내려갈 때마다 **시간이나 공간 중 하나를 확실히 개선**하고, 마지막 줄은 둘 다 최적이다. "메모이제이션 = 공간을 내주고 시간을 사는 것"이라는 말이 정확히 2행에서 3행이 아니라 **1행에서 2행**의 이야기임에 주의하자.

**왜 이렇게 되는가**

- **무엇을 세는지부터 정한다**: 공간복잡도는 보통 **보조 공간(auxiliary space)** — 입력을 담는 공간과 답을 담는 공간을 뺀, 알고리즘이 스스로 추가로 잡는 메모리 — 를 뜻한다. 길이 `n` 리스트를 반환하는 함수를 "공간 `O(n)`"이라 부를지 "`O(1)`"이라 부를지는 이 기준을 어디에 두느냐의 문제이므로, 답하기 전에 기준을 한 줄 밝히는 것이 안전하다.

- **왜 형제 호출은 더하지 않는가**: 호출 스택에는 **"아직 반환하지 않은" 프레임만** 남는다. `f`가 `g`를 부르고 `g`가 끝나서 반환하면 `g`의 프레임은 즉시 사라지고, 그 뒤에 `f`가 `h`를 부른다. 따라서 어느 순간에도 스택에 있는 것은 **루트에서 지금 실행 중인 노드까지의 한 경로**뿐이다. 그래서 공간은 노드 수가 아니라 **트리의 높이**가 된다.

  - 나이브 피보나치: 시간 `O(2ⁿ)`(노드 수)인데 공간은 `O(n)`(높이). 이 둘이 크게 벌어지는 대표 예다.
  - 병합 정렬: 스택은 `O(log n)`이지만 병합용 보조 배열이 `O(n)`이라, 둘의 **최댓값**인 `O(n)`이 답이다. 여러 종류의 공간이 있으면 합이 아니라 "동시에 살아 있는 것들의 합의 최댓값"을 본다.

- **파이썬의 재귀 한도가 존재하는 이유**: 파이썬은 기본적으로 재귀 깊이를 약 1000으로 제한한다. 스택은 프로세스가 미리 잡아 둔 유한한 메모리 영역이라, 무한 재귀가 그 영역을 넘어 다른 메모리를 덮어쓰는 사고를 막으려는 안전장치다. 따라서 **깊이가 `n`에 비례하는 재귀는 `n`이 수천만 넘어가도 실행 자체가 불가능**하다. 이때의 해법은 두 가지다.

  - 재귀를 반복문으로 바꾼다(깊이 → `O(1)`). 이진탐색·팩토리얼·리스트 합이 여기 해당한다.
  - 재귀 구조가 본질적이면 명시적 스택(리스트)에 상태를 쌓아 직접 관리한다. 스택 프레임 대신 힙 메모리를 쓰게 되어 한도에 걸리지 않는다.

  즉 재귀의 공간복잡도는 "메모리를 얼마나 쓰나"를 넘어 **"이 코드가 아예 돌 수 있는가"**의 문제이기도 하다.

- **숨은 공간 — 슬라이싱**: `a[:mid]`, `a[mid:]`는 새 리스트를 **복사해서 만든다**. 재귀에 그대로 넘기면 시간뿐 아니라 공간도 각 레벨에서 `O(n)`이 추가된다. 인덱스 `lo`, `hi`만 넘기면 복사가 사라져 보조 공간이 `O(1)`(+스택)이 된다. 재귀에 배열을 넘길 때 **"자르지 말고 범위를 넘겨라"**가 정석인 이유다.

- **시간과 공간은 독립이다**: 이중 반복으로 최댓값 쌍을 찾는 코드는 시간 `O(n²)`이지만 변수만 쓰므로 공간 `O(1)`이다. 반대로 길이 `n` 집합을 만들어 한 번 훑으면 시간 `O(n)`·공간 `O(n)`이다. **한쪽이 크다고 다른 쪽이 크지 않다** — 항상 따로 센다.

- **트레이드오프를 결정하는 기준**: 제한 시간이 병목이면 표를 만들어 시간을 사고(누적합·메모·해시), 메모리 제한이 병목이면 제자리(in-place) 갱신·두 변수 롤링·정렬 후 훑기로 공간을 아낀다. 코테에서는 대개 시간이 먼저 터지므로 **"공간 `O(n)`을 써서 시간 등급을 한 칸 낮춘다"**가 기본 전략이지만, `n²` 크기의 표를 잡는 순간(`n = 10⁵`이면 `10¹⁰`칸) 메모리가 먼저 죽는다는 점도 함께 기억해야 한다.

**접근 전략**

- 핵심 아이디어: "입력 말고 내가 새로 만든 저장 공간이 `n`에 따라 커지는가?"를 물어라. 커지지 않으면 `O(1)`, 리스트 하나면 `O(n)`, 표 하나면 `O(n²)`. 재귀라면 "동시에 살아 있는 스택 프레임의 최대 깊이"를 반드시 더한다.
- 전형 절차: (1) 반복 중 크기가 `n`에 비례해 자라는 컨테이너가 있는지 본다, (2) 재귀면 최대 호출 깊이를 계산한다(같은 시점에 살아 있는 것만 — 형제 호출은 순차 반환되므로 동시 존재 아님), (3) 둘의 최댓값이 공간복잡도. 파이썬 슬라이싱 `a[1:]`은 새 리스트를 만들어 숨은 `O(n)` 공간을 쓴다는 점을 주의한다.
- 복잡도(주의점): 시간과 공간은 다르다 — 시간이 `O(n²)`라도 공간은 `O(1)`일 수 있다(이중 반복이지만 변수만 쓰면). 흔한 실수: 재귀 스택 공간을 빼먹는 것, 그리고 반환값을 담는 리스트를 "출력이니까 안 센다"고 넘겨 auxiliary와 output 기준을 뒤섞는 것. 문제에서 무엇을 세는지 기준을 먼저 정하라.

**문제**

```runner
(2) 코드 단계별
```

**2) 이진탐색 두 버전의 공간** · Medium

- **요구사항**: 정렬 배열에서 이진탐색을 (a) `while` 반복으로 구현할 때와 (b) 재귀로 구현할 때의 공간복잡도를 각각 구하고 차이를 설명하라. 시간복잡도는 둘 다 같음을 확인하라.
- **입력**: 정렬 배열, 찾을 값
- **출력**: (a)(b) 공간복잡도와 차이 설명, 공통 시간복잡도
- **예제**: `n=1,000,000` → 반복형 스택 깊이 1(=`O(1)`) / 재귀형 최대 깊이 약 `log₂(10⁶)≈20`(=`O(log n)`)
- **셀프체크**: 시간은 둘 다 `O(log n)`으로 동일한가? 재귀형이 `O(log n)` 공간을 쓰는 이유가 스택 프레임임을 짚었는가? 반복형은 인덱스 변수만이라 `O(1)`인가?

```runner
@@SOLUTION
import sys
n = int(sys.stdin.readline())
depth = 0
size = n
while size >= 1:
    depth += 1
    size //= 2
print('iter', 'O(1)')
print('rec', 'O(log n)', depth)
print('time', 'O(log n)')
@@TESTS
--IN
1000000
--OUT
iter O(1)
rec O(log n) 20
time O(log n)
--IN
1000
--OUT
iter O(1)
rec O(log n) 10
time O(log n)
@@EXPL
(1) 접근·핵심 아이디어

- 두 이진탐색은 시간은 같지만(`O(log n)`) 공간이 다르다. (a) `while` 반복형은 `lo`/`hi` 같은 인덱스 변수 몇 개만 쓰므로 추가 공간 `O(1)`. (b) 재귀형은 절반씩 좁히며 자기 자신을 호출해 최대 `log2 n` 깊이의 스택 프레임이 쌓여 공간 `O(log n)`. 그 깊이를 실제로 세어 보여준다.

(2) 코드 단계별

- 배열 크기 `n`을 읽는다.
- `size`를 절반씩 줄이며 몇 번 만에 0이 되는지 세어 재귀 최대 깊이(≈`log2 n`)를 재현. n=10^6이면 약 20, n=1000이면 약 10.
- 반복형 공간 `O(1)`, 재귀형 공간 `O(log n)`과 실제 깊이, 공통 시간 `O(log n)`을 출력.

(3) 스스로 다시 짤 때 생각 순서

- 두 구현의 "탐색 범위 절반씩 줄이기"는 동일 → 비교 횟수 log n → 시간 O(log n) 공통.
- 반복형은 상태가 인덱스 변수뿐 → 추가 공간 O(1).
- 재귀형은 반환 전까지 프레임이 쌓임 → 동시에 살아 있는 최대 깊이 = log n → 공간 O(log n).
- 깊이를 확인하려면 n을 절반씩 나눠 1 이하가 될 때까지의 횟수를 센다.
```

**3) 중복 제거의 공간-시간 선택** · Medium

- **요구사항**: 길이 `n` 리스트의 중복을 제거하려 한다. (a) `set`에 이미 본 값을 담아가며 걸러내는 방식의 시간·공간복잡도, (b) 정렬 후 인접 중복만 제거하는 방식의 시간·공간복잡도를 각각 구하고, 언제 어느 쪽이 나은지 한 줄로 판단하라(구현 금지).
- **입력**: 길이 `n` 리스트
- **출력**: (a)(b) 각각의 시간·공간복잡도와 선택 기준
- **예제**: `[3,1,3,2,1]` → 유일값 `{1,2,3}` / `set` 방식은 입력 순서 보존, 정렬 방식은 값 순서로 정렬됨
- **셀프체크**: (a)가 시간 `O(n)`·공간 `O(n)`(집합 저장)인가? (b)가 시간 `O(n log n)`(정렬 지배)·공간은 정렬 방식에 따라 `O(1)`~`O(n)`인가? "순서 보존이 필요하면 (a), 추가 공간을 아끼려면 (b)"처럼 트레이드오프로 답했는가?

```runner
@@SOLUTION
import sys
data = sys.stdin.read().split('\n')
a = list(map(int, data[0].split())) if data[0].strip() else []
seen = set()
order = []
for x in a:
    if x not in seen:
        seen.add(x)
        order.append(x)
print(' '.join(map(str, order)))
print(' '.join(map(str, sorted(seen))))
@@TESTS
--IN
3 1 3 2 1
--OUT
3 1 2
1 2 3
--IN
5 5 4 4 4 1
--OUT
5 4 1
1 4 5
@@EXPL
(1) 접근·핵심 아이디어

- (a) `set`에 이미 본 값을 담아가며 걸러내면 각 검사·삽입이 평균 `O(1)`이라 시간 `O(n)`, 집합 저장에 공간 `O(n)`. 장점은 입력 순서 보존. (b) 정렬 후 인접 중복만 제거하면 정렬이 지배해 시간 `O(n log n)`, 공간은 정렬 구현에 따라 `O(1)`~`O(n)`. 결과는 값 순서로 나온다. 두 결과(순서 보존판·정렬판)를 함께 출력해 차이를 드러낸다.

(2) 코드 단계별

- 입력 리스트를 읽는다.
- `set`으로 처음 보는 값만 `order`에 순서대로 추가 → (a)의 "입력 순서 보존 중복 제거".
- `sorted(seen)` → (b)의 "값 순서로 정렬된 중복 제거" 결과. `[3,1,3,2,1]`은 순서 보존판 `3 1 2`, 정렬판 `1 2 3`.

(3) 스스로 다시 짤 때 생각 순서

- 두 목표를 구분: (a) 순서 유지 + 빠른 시간(set, O(n) 시간/공간), (b) 공간 절약 가능 + 정렬된 출력(O(n log n) 시간).
```
